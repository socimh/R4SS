18  Import and export

This chapter opens Manage datasets. After exploring tables and working with individual variables, we consider how to bring files into R, preserve their metadata, and save checked results. You can return here whenever a project supplies a different format.

The first download and CSV import in Section 7.7 introduced the route from a file to a table, and Section 7.8 saved a separate copy. This chapter extends that workflow to different formats, metadata, and sources. Return here when an unfamiliar file, a label, or a conversion requires more than the basic reader.

By the end of this chapter, you will be able to:

  • Locate a declared source file and distinguish a file from an R object.
  • Read CSV, Stata, and SPSS data and check the meaning of their columns.
  • Specify missing tokens and column types, then inspect parsing and metadata.
  • Export separate copies and check what survives when they are reopened.

We reuse selection, conversion, missing-value checks, and column inspection from earlier chapters. All examples use the historical country data, with two six-country format excerpts and the complete package dataset. This chapter needs three files in examples: lifeexp-excerpt.dta, lifeexp-excerpt.sav, and lifeexp.csv. No GSS file is required.

18.1 A workflow in R

So far, packaged data and a saved survey extract have supplied our tables. When a research archive supplies a file, we need to bring it into R and check what the format preserves.

My view is that learning to work comfortably with tibbles is enough to carry out most data analysis.

Files on disk and objects inside R are different things. For many tabular analyses, we can organize the work in three steps, which connect the earlier table operations to files on disk:

  1. Import data from another format as a tibble (Section 18.2).
  2. Process the tibble with the selection and transformation tools already learned.
  3. Export the tibble to another format (Section 18.4).

Imagine receiving a household survey from a research archive. The archive is the source, the downloaded Stata file is the format, and the tibble you import is an R object in your current session. Changing the format does not, by itself, change whom the survey represents or what its questions mean. A codebook describes the variables, their values, and important details of data collection. Keep it with the data: importing a file successfully does not tell you how to interpret its contents.

18.2 Importing data

The same survey may be offered in several formats. Choose among those supplied by the producer before converting anything yourself: a labelled statistical file may carry information that a plain-text copy leaves to a separate codebook. Use Table 18.1 as a reference when you receive a file, rather than as a list to memorize. Functions without a prefix come from base R or from readr, readxl, and haven, which are installed with the tidyverse; a function written as package::function() comes from a package you may need to install first.

Data can also come from inside R: datasets included with R and its packages, or values typed directly into code, as in the named-country example in Introduction to R. Folders can hold several data files at once. Text, images, and recordings may require other tools before they yield the variables needed for a particular analysis. These lists are not exhaustive. A small file is not necessarily a simple dataset.

R reads these formats with short commands. The examples below use two small files containing the same six countries: lifeexp-excerpt.dta and lifeexp-excerpt.sav. The haven package, installed with the tidyverse, reads both. In the printed tibble, the header gives rows first and columns second: 6 × 6 means six countries and six variables. Numbers at the left mark row positions, not respondent IDs. Under each column name, a cue such as <dbl> identifies its type; <dbl> means a numeric column stored as doubles:

Before running the import, open the r4ss project folder you created in Section 1.1.1 and check it with getwd(). Inside it, create a subfolder named examples using your file manager or editor. Download both linked files and move them into that subfolder, keeping their exact names. A browser may initially save them in Downloads; clicking the links alone does not place them in examples.

The relative path "examples/lifeexp-excerpt.dta" tells R to start in its working directory, enter examples, and read lifeexp-excerpt.dta. The same convention applies to the SPSS file. To check the locations before importing, file.exists() returns TRUE for each file R can find:

These countries are a purposeful teaching selection, not a representative sample of countries. The packaged snapshot is historical; it is not a source of current country estimates. Once the data are in R, these meanings remain the same whichever file format we read.

Importing and exporting are checks at the boundaries of an analysis. A file that opens without an error can still have the wrong sheet, a misread date, or an identifier that has lost its leading zeros. Table 18.2 lists what to check at each stage.

For restricted data, use only the export and release procedures permitted by the provider. Changing from a statistical file to CSV does not change the conditions governing its use.

18.2.1 Where data come from

Your research question helps determine what counts as an observation. A sociologist might study people or organizations; an economist might study households, firms, or countries; a political scientist might study voters, elections, or legislative speeches. These boundaries overlap: a household survey can support questions about employment, family life, health, and political participation. Table 18.3 gives starting points, not a ranking of what each discipline uses most.

A subject label alone cannot tell us which file format to expect. The format depends on how the material was collected and distributed: a survey might arrive as a statistical file or CSV, election returns as a spreadsheet, online posts as JSON or text, and interviews as transcripts and recordings.

TipGetting access to data

Access follows the collection’s conditions, not the name of your discipline. Some files are openly downloadable; others require registration and an agreement, a university subscription, or a research partnership. More sensitive records may require a project application, training, and work inside a secure computing environment. “Free of charge” does not necessarily mean unrestricted reuse. Detailed locations, school records, and linked administrative records can have tighter access conditions than published summaries, and platform terms and participant consent may limit collection or reuse.

Students can use many of the same archives as established researchers, although particular collections have their own eligibility rules. The UK Data Service lets students and researchers from different disciplines and countries register; its access policy distinguishes open, safeguarded, and controlled data. IPUMS International provides census microdata without charge after an access application, subject to conditions on use. ICPSR notes that students generally need a faculty sponsor for restricted-data applications, and the Qualitative Data Repository distinguishes standard access from project-specific conditions. These are examples of access arrangements, rather than promises that any particular file will be available to every reader.

For a first project, choose a documented dataset that you can actually obtain within the time available, with a question its contents can answer.

18.3 Specify the CSV import

We continue with all 68 countries and six variables in lifeexp, using countries as a working name. The assignment below retains the source’s observations, order, missing values, and labels. We keep this object for comparison with the imported copy.

library(tidyverse)
library(tidystata)
countries <- lifeexp

Research data also arrive as files. To practice importing the same observations, download lifeexp.csv and save it in the examples folder inside your r4ss project. This file contains every row and column from the supplied lifeexp, in its original order. Its dataset notes give the source, units, and missing-value convention. The Stata and SPSS examples above in Section 18.2 use a smaller excerpt; here we use the complete dataset.

There is another import decision to check: the country name identifies each row. The first import correctly inferred character storage, but an explicit specification makes our expectation clear when the file is read again.

A collector specifies how readr should read a column. It is an instruction for an import, not a conversion of an existing column. Introduce the collectors separately. col_character() requests text:

col_character()
<collector_character>

The printed collector describes an expected type; it contains no country observations. Use it for country names, whose letters should remain text. col_integer() requests whole numbers:

col_integer()
<collector_integer>

Our documented region codes are whole numbers, so integer storage fits them. This does not make region a quantity: 1, 2, and 3 identify categories, and their average has no substantive meaning.

col_double() requests numeric values that can include fractional parts:

col_double()
<collector_double>

Use doubles for the measured variables. Population growth includes decimals, and the other recorded measurements are numeric quantities even where the captured values have been rounded to whole numbers.

cols() combines named collectors into one column specification. Each name identifies a CSV column; the collector on its right specifies its expected type. Begin with selected columns:

selected_types <- cols(country = col_character(), region = col_integer())
selected_types
cols(
  country = col_character(),
  region = col_integer()
)

The printout lists the two explicit instructions; unspecified columns still use guessed types. Supply this object to read_csv() through col_types, retaining the documented missing-token rule:

countries_csv <- read_csv(
  "examples/lifeexp.csv",
  na = c("", "NA"),
  col_types = selected_types
)
var_type(countries_csv$country)
[1] "character"
var_type(countries_csv$region)
[1] "integer"

The checks report character country names and integer region codes. We have reread the unchanged file with explicit expectations, rather than repaired it after importing.

To specify every column, the .default option in cols() supplies the collector for columns not named individually. Here all remaining columns are documented numeric measurements. Keep names as character and region as integer:

country_types <- cols(
  .default = col_double(),
  country = col_character(),
  region = col_integer()
)
country_types
cols(
  .default = col_double(),
  country = col_character(),
  region = col_integer()
)

This specification covers the file’s six columns without guessing. It is appropriate to this documented file, not a rule that every unlisted column in a future dataset must be numeric. Import again with it:

countries_csv <- read_csv(

The import retains 68 countries. Types now follow the specification; the next check asks whether any source entries failed those rules.

An import can return a table while reporting values it could not parse as requested. Readr’s problems() receives the imported table and returns a diagnostic table without changing its values:

problems(countries_csv)
# A tibble: 0 × 5
# ℹ 5 variables: row <int>, col <int>, expected <chr>, actual <chr>, file <chr>

Here the result has zero rows: readr recorded no parsing problems in this import. The headings show what a problem report would contain. row and col locate the source entry; expected describes what the parser required, and actual records what it encountered. file identifies the source file. If rows appear, inspect those entries in the unchanged CSV and compare them with its documentation and your type and missing-token specifications. Correct the import rule only when the source supports that correction, then import and check again.

A zero-row report does not certify that the observations, units, or identifiers are correct. Continue the type, missingness, and source comparisons below. Hiding an import message would not repair a parsing problem.

Readr’s imported tibble carries additional import information; var_type() reports its table type. It is still a table. The CSV has names but no variable-label metadata; the package object has both. Different table metadata do not imply different observations. CSV contains values and names but does not retain the source’s variable and value labels. The original countries object still holds those labels; countries_csv lets us inspect what the file format preserves. Here region is a numeric code: 1 is Europe and Central Asia, 2 North America, and 3 South America. These codes are categories, not quantities to average.

The file opened without an error at each stage, but a useful import also follows its documented missing codes and gives important columns suitable types. Keep the original file unchanged. After checking values and metadata, we can save derived files under new names and reopen them, as the next section demonstrates.

Other formats follow a similar pattern: a reading function brings a file into R, and a writing function saves an object to a file. Table 18.4 is a reference for choosing the package and function, not a requirement to install every package now. The import and export examples in Section 18.2 explain these boundaries further.

18.4 Exporting results

R can write many of the formats in Table 18.1, although an exported file may not retain every feature of the original. The useful distinction is between data someone will analyze and results someone will read. A collaborator checking your analysis needs usable values and documentation; a reader of an article usually needs a clearly labelled table or figure. A screenshot of a table may be convenient for a conversation, but it is a poor substitute for the underlying values when someone needs to recalculate a result.

Table 18.5 connects common purposes to possible outputs. More than one choice can be sensible; the best depends on the recipient’s tools and the information that must survive the handover.

An RDS file is a working copy for repeated work within R, not a universal exchange format. Parquet’s compression and column-oriented storage matter most when your tools can use them. A PNG stores pixels, so its export dimensions affect how readable its labels will be; SVG and PDF can preserve vector lines and text. Here, a vector graphic stores shapes and drawing instructions so that they can be resized; it does not mean an R vector of values. Whatever the output, retain the source code so that you can regenerate it.

18.4.1 Save and reopen a CSV

write_csv() takes a table first and a destination path second. It writes column names and values to a text file, returning without a console table. Use a new name to preserve the source. The output path has no folder prefix, so it is relative to the working directory:

write_csv(countries_csv, "countries-checked.csv")

A saved file remains after the R session ends. Reopen it into a separate object, using the same documented type and missing-token rules:

countries_csv_saved <- read_csv(
  "countries-checked.csv",
  na = c("", "NA"),
  col_types = country_types
)

18.5 Check your file workflow

Use the familiar file.exists() check to locate a saved copy:

file.exists("countries-checked.csv")
getwd()

The first result should be TRUE after the CSV export. Because the path has no folder prefix, the file is directly in the directory reported by getwd(). Locate it in your file manager. Saving the script preserves instructions; exporting preserves a data file; assignment alone keeps an object only in the current R session.

Check the whole route in a fresh session: open the same project, load the required packages, rerun the import and its specification, then reopen an export into a separate object. Explain which item is a source file, which is an R object, and which is a derived file. Choose output names that do not overwrite your original downloads or another result you need to preserve.

There is no need to learn every format now. Begin with the file your project supplies, understand its rows and columns, and choose an output the next person can use. A successful conversion preserves the meaning of the information, not just the number of rows.

18.6 Review

  • getwd() reports the working directory, and file.exists() checks a specified path.
  • read_csv(), read_dta(), and read_sav() import CSV, Stata, and SPSS files; inspect rows, types, missing-value codes, and labels.
  • col_character(), col_integer(), and col_double() specify expected column types; cols() combines those instructions.
  • problems() reports recorded parsing issues; a zero-row report does not validate meanings or units. var_type() and variables() help inspect types and metadata.
  • write_csv() and write_dta() export tables; write_rds() and read_rds() preserve and restore an R object. Reopen separate copies to check the relevant values, types, and labels.
  • Optional: spec() reports an import specification, write_parquet() exports a Parquet file, and as_flextable() creates a report-style formatting object.
